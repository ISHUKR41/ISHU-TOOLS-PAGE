## STEP 3 — FALLBACK SYSTEM FOR EVERY TOOL (CRITICAL)

Many tools in this project work initially but **stop working after some time** — due to API failures, rate limits, network issues, timeout errors, or state corruption. You must implement a **complete fallback and recovery system** for every single tool. This is not optional.

**For every tool, implement ALL of the following:**

### A) Error Boundary Protection
* Wrap every tool component in a React Error Boundary
* If a tool crashes or throws an error, show a clean fallback UI instead of a blank screen or broken page
* The fallback UI must show a friendly message like "Something went wrong. Click here to reload this tool." with a retry button
* The retry button must reset the tool's state completely and reinitialize it fresh

### B) API & Network Fallback
* For any tool that calls an external API or service, implement this fallback chain:
  1. Try the primary API/method first
  2. If it fails or times out, automatically try a secondary backup API or method
  3. If both fail, fall back to a local/offline version of the tool that works without any internet connection (even if limited)
  4. Show the user a clear status message at each stage — "Trying backup...", "Running in offline mode..."
* Set a proper timeout (maximum 8 seconds) on every API call — never let a tool hang indefinitely
* Use `try/catch` with `async/await` on every single API call — no unhandled promise rejections

### C) Auto-Retry Logic
* If a tool fails, automatically retry up to 3 times with a 2-second delay between each retry
* Show a visible retry counter to the user: "Retrying... (attempt 2 of 3)"
* After 3 failed retries, show the fallback UI with a manual retry button
* Implement exponential backoff if rate limiting is suspected

### D) State Recovery & Reset
* Every tool must have a "Reset / Reload Tool" button always visible
* If a tool's internal state becomes corrupted or stuck, pressing reset must restore it to its initial working state without refreshing the entire page
* Use `useReducer` or clean `useState` initialization so state can be fully reset on demand
* Save tool state to `localStorage` where appropriate so users don't lose their work if the page refreshes

### E) Loading & Timeout States

* Every tool must show a proper loading spinner or skeleton UI while processing
* If loading takes more than 8 seconds, automatically cancel the request and show: "This is taking too long. Please try again." with a retry button
* Never leave a tool in an infinite loading state

### F) Offline Detection
* Detect when the user's internet connection drops using the `navigator.onLine` API and the `online`/`offline` window events
* When offline is detected, immediately show a banner: "You are offline. Some tools may have limited functionality."
* Tools that can work offline (calculators, text tools, converters, etc.) must continue working normally even when offline
* Tools that require internet must clearly show they need a connection, with a "Retry when online" button that auto-triggers when connection is restored

### G) Rate Limit Handling
* If any tool uses a rate-limited API, track usage with a local counter
* When the rate limit is hit, show a clear message: "Rate limit reached. Please wait X seconds before trying again." with a visible countdown timer
* After the countdown, automatically re-enable the tool

### H) Graceful Degradation
* Every tool must have at least a basic working version that functions without any external dependencies
* If a premium feature or API-dependent feature fails, the core functionality of the tool must still work
* Never let one failing feature break the entire tool

### I) User Feedback on Errors
* Never show raw error messages, stack traces, or technical jargon to the user
* All error messages must be human-friendly and actionable
* Always offer the user a clear next step: retry, reset, go offline mode, or contact support
